# v1.4-#2: Shared Kuzu DB Prototype — Measurement & Recommendation

## Scope

Prototype the session-scoped shared Kuzu DB pattern on ONE pilot directory
(`tests/knowledge_graph/store/`) and measure whether it materially reduces
per-test memory/disk footprint vs. the per-test
`KGStore.open(tmp_path / "kg.kuzu")` baseline.

The pilot migration covers 6 tests in `test_origin_gc.py`:

- `test_prune_single_orphan`
- `test_prune_keeps_live_origins`
- `test_prune_facade_export`
- `test_extract_gc_idempotent_on_clean_corpus`
- `test_extract_gc_true_no_orphans_reports_zero`
- `test_extract_gc_pruned_via_no_touched_paths_branch`

The remaining 10 tests in the file stay on `tmp_path` because they either
exercise replacement-merge semantics that conflict with shared-DB residue,
use multiple ad-hoc corpus tags, or run cross-source assertions that would
need substantial re-tooling.

## Method

Both runs:

```
rm -rf ~/.pytest-tmp
/usr/bin/time -f "WALL=%e PEAK_RSS_KB=%M" \
    .venv/bin/pytest tests/knowledge_graph/store/test_origin_gc.py -v --timeout=300
du -sb ~/.pytest-tmp/
```

Single-shot, no warm-up, no re-run averaging. Numbers below are wall-clock
seconds, peak RSS as reported by GNU time, and post-run `~/.pytest-tmp/`
disk residue in bytes.

## Results

### Baseline (per-test `KGStore.open(tmp_path / ...)`)

| metric          | value          |
| --------------- | -------------- |
| wall            | 291.04 s       |
| peak RSS        | 469 612 KB     |
| disk residue    | 427 985 881 B  |
| pass / total    | 16 / 16        |

### Prototype (6 tests migrated to `shared_kuzu_store`)

| metric          | value          |
| --------------- | -------------- |
| wall            | 301.96 s       |
| peak RSS        | 913 548 KB     |
| disk residue    | 257 031 177 B  |
| pass / total    | 16 / 16        |

### Delta

| metric          | baseline      | prototype     | delta             |
| --------------- | ------------- | ------------- | ----------------- |
| wall            | 291.04 s      | 301.96 s      | +3.8 %  (worse)   |
| peak RSS        | 458 MB        | 892 MB        | +95 %   (worse)   |
| disk residue    | 408 MB        | 245 MB        | −40 %   (better)  |
| pass count      | 16            | 16            | 0                 |

## Interpretation

**Disk:** the prototype shaves ~163 MB off `~/.pytest-tmp/` residue,
even though only 6/16 tests were migrated. Extrapolating: if all 16 had
been migration-eligible, disk savings would plausibly land in the
3–4× range. So the *direction* is correct — fewer per-test DB
materialisations = less disk.

**Wall-clock:** essentially flat (+3.8 %, well within run-to-run noise
for a 5-minute pytest). The shared DB does not buy speed on this file
because the dominant cost is `extract()` (full pyslang elaboration), not
DB open/close.

**RSS:** the prototype's *peak* RSS roughly doubled (458 MB → 892 MB).
The session DB stays mmap'd for the whole pytest run while sibling tests
also load their own per-test DBs (the 10 unmigrated tests). This is the
expected cost of a coexistence period — pure additive overhead while
both patterns live in the same session.

## Conclusion

**Recommendation: HOLD.**

Reasons:

1. The disk win (−40 %) is real but well **under** the 2× bar set in
   the prototype charter.
2. Wall-clock is not improved — the bottleneck is `extract()` CPU, not
   per-test DB I/O.
3. Peak RSS *regresses* badly during coexistence: the session store and
   the per-test stores both live in memory. A full rollout would close
   this gap (no more per-test stores → only the session DB is
   resident), but partial migrations are strictly worse.
4. The corpus-scoping refactor required per test is non-trivial: every
   `_origin_ids()`, every `prune_orphaned_origins()`, every `extract()`
   call has to be scoped explicitly. Tests that currently exercise
   "the whole DB" semantics (no filter) cannot be migrated at all
   without changing what they assert.
5. The original symptom — `/tmp` tmpfs saturation — was already
   addressed by v1.4-#1 (basetemp redirect to `~/.pytest-tmp` on the
   root filesystem). The disk-saturation risk that justified this
   prototype is currently mitigated by a much cheaper change.

The fixture itself is sound (all 8 fixture-coverage tests pass, all 6
migrated tests pass alongside the unmigrated 10), so the
**code can stay merged** as opt-in infrastructure. But a repo-wide
rollout in v1.4-#3 is **not** justified by these numbers.

## Followups (if rollout were to proceed despite this recommendation)

- Audit every store test for `extract()` / `prune_orphaned_origins()`
  call-sites that assume an empty DB; rewrite them to be corpus-scoped.
- Migrate `tmp_store` itself to be a thin wrapper that yields
  `(store, corpus)`; drop the per-test DB path entirely.
- Re-measure ONLY after the full migration; the partial-migration RSS
  regression makes any intermediate number misleading.
- Investigate whether Kuzu's mmap footprint scales with session
  lifetime; the prototype's +434 MB RSS bump is alarming if the same
  DB is shared across ~2500 tests.

## Followups for v1.4-#3 (independent of rollout decision)

- Document `shared_kuzu_store` in `tests/README.md` as opt-in
  infrastructure for future test authors who DO want session-scoped
  isolation.
- Consider scoping the disk-saturation risk monitoring separately —
  add a CI step that fails if `~/.pytest-tmp/` exceeds N GB after a
  full pytest run. Cheaper insurance than a structural migration.

## Issues discovered

None — fixture works end-to-end. No KGWeave bugs surfaced. Kuzu happily
handles concurrent corpus namespaces within a single DB.
