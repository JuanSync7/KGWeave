# v1.6-#1 diagnosis — md↔sv lift/promote cache pollution

## Failing tests (red baseline)
- `tests/knowledge_graph/builders/md/test_isolation_i7.py` — passes alone
  but its `extract(source="sv", paths=[fifo.sv, fifo_pkg.sv])` (note the
  **fifo-first** order) poisons the SV promote cache.
- `tests/knowledge_graph/builders/sv/legacy_tests/rules/test_types.py`
  `::test_s32_wildcard_import_edge_from_fifo`,
  `::test_s32_explicit_item_import_edge_from_fifo`,
  `::test_s50_does_not_disturb_s32_imports_edges` — assert real `imports`
  edges from the `fifo` module to the `fifo_pkg` package, all three flip
  to **zero matches** after the i7 prelude.

## Mechanism
- The MD-test `extract` and the SV-legacy `build_kg` resolve to the **same
  uri** (`tests/.../builders/sv/corpus/` is a **symlink** to
  `tests/.../fixtures/sv/`). Same `(uri, sha)` for both fixtures.
- `compute_corpus_fp` in `src/knowledge_graph/builders/sv/semantic/promote_cache.py`
  hashes the **sorted** `[(uri, sha), ...]` list. Sorting strips file
  ORDER from the fingerprint.
- The SV promote dispatch is **order-sensitive**: when `fifo.sv` runs
  promote BEFORE `fifo_pkg.sv` has been pass1'd, the `imports` edge from
  the `fifo` module is wired to the synthetic `_unresolved.fifo_pkg`
  placeholder (the package isn't in `semantic_name_index` yet at that
  point in the walk).
- The MD test passes `[fifo.sv, fifo_pkg.sv]`; the legacy test passes
  `[fifo_pkg.sv, fifo.sv]`. Different file ORDER, same `corpus_fp`.
  The legacy test gets a **cache hit** and replays the MD-order delta
  with `_unresolved.fifo_pkg` dst — exactly the failure observed.

## Fix shape chosen
Make `compute_corpus_fp` **order-preserving**. The corpus fingerprint
should reflect the exact sequence of files presented to `build_kg`, not
the set. Drop the `sorted(...)` and hash the list as-given.

## Why this fix
- Smallest change that closes the loophole.
- Matches reality: promote's behaviour is a function of `(files, order)`,
  so the cache key must encode both.
- Same-corpus re-runs with identical ordering still hit the cache (the
  hot-path the promote cache exists for).
- No public API change; no behaviour change for callers that present
  files in stable order (which `extract`'s `_prefix_for_path` loop already
  does).
